Implement the Driver verification workflow described below.

IMPORTANT:

* Do NOT replace the existing Driver authentication, onboarding, document upload, private storage, or Admin authentication architecture.
* Do NOT create duplicate Driver/application/document tables or duplicate approval APIs.
* Extend and wire the existing implementation.
* Make the smallest safe changes necessary.
* Do not weaken any existing authorization or security controls.

Phase 1 — Repair the Admin Driver review UI

The existing Admin Drivers page incorrectly checks:

row.status

The API returns:

row.approvalStatus

Fix this mismatch everywhere in the Admin Driver review UI.

The Admin Drivers page must correctly show:

* Pending
* Approved
* Rejected
* Suspended

Add proper:

* Loading state
* Error state with Retry
* Genuine empty state
* API failure handling

Pending Drivers must display a clear action to open their review.

Create a usable Admin Driver review/detail screen showing the information already returned by the endpoint:

Documents

Use the existing:

Do not create a second document-review API.

Add an appropriate rejection-reason field when rejecting a document.

Phase 3 — Secure Admin document viewing

Add one narrowly scoped Admin-only endpoint:

POST /api/admin/driver-documents/:id/download-url

Requirements:

* Admin role required.
* Dispatcher must NOT be allowed.
* Look up the document by ID.
* Validate the document belongs to the referenced Driver.
* Validate the storage path is a private Driver-document path.
* Generate a short-lived signed GET URL using the existing private document storage implementation.
* Never expose permanent/public storage paths.
* Do not make Driver documents publicly accessible.
* Handle missing documents safely.

If appropriate for the existing audit architecture, record an Admin document-access audit event.

The Admin UI should provide:

* View
* Open
* Download

using the short-lived signed URL.

Do not expose storagePath to the browser as a permanent path.

Display MVR status in the Admin Driver review screen.

Phase 6 — MOST IMPORTANT: Make approval authoritative server-side

Do NOT create a new approval endpoint.

Strengthen the existing:

POST /api/admin/drivers/:id/decision

Approval must happen only if ALL of the following are true.

Application requirements

1. Driver exists.
2. Driver application exists.
3. onboarding_status === submitted
4. Required onboarding fields are complete.

Required documents

The latest/current document for each required type must exist and have:

* verification_status === approved

Required:

* License
* Insurance
* Vehicle registration

Also verify that required documents are not expired.

Insurance

Verify:

* Insurance document is approved.
* Insurance expiration is in the future.
* Existing structured insurance expiration is valid.

Background check

Require:

background_check_status === clear

MVR

Require:

mvr_check_status === clear

Account eligibility

Verify the Driver/account is in an eligible state and is not suspended or otherwise blocked.

If ANY requirement fails:

* Do NOT approve.
* Return HTTP 409 or 422.
* Return a structured list of unmet requirements.

Example response shape:

{
  "error": "Driver verification incomplete",
  "requirements": [
    {
      "code": "BACKGROUND_CHECK_NOT_CLEAR",
      "message": "Background check must be clear before approval."
    },
    {
      "code": "INSURANCE_DOCUMENT_PENDING",
      "message": "Insurance document must be approved."
    }
  ]
}

Do not leak unnecessary private document information.

Approval transaction

Inside the existing approval transaction, atomically update:

* drivers.approval_status = approved
* drivers.onboarding_status = approved
* drivers.availability_status = offline
* Appropriate profile status
* Existing Admin audit log

Make sure there is no state where approval is committed but the related lifecycle state is only partially updated.

For rejection/suspension, make related lifecycle updates consistent with the existing product behavior.

Important: document selection

The database permits multiple document versions.

When checking approval eligibility, select the latest/current document for each required document type according to the existing application logic.

Do not accidentally approve a Driver because an older document is approved while a newer replacement is pending or rejected.

Phase 7 — Prevent verification bypass

Review all server-side Driver lifecycle paths.

Going online must remain protected by approval.

Offer listing must remain protected by approval.

Offer acceptance must remain protected by approval.

Do not rely on frontend hiding buttons.

The server must remain authoritative.
